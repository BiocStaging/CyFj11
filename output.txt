I have not modified any code. Here is what I found and my targeted suggestions for `export_flowjo10_workspace`.

## XML schema differences

The **overall XML schema / namespace declarations are the same** in both versions:

- `version="20.0"`
- `flowJoVersion="10.10.1"`
- Same namespaces: `xsi`, `gating`, `transforms`, `data-type`
- Same `xsi:schemaLocation` pointing to Gating-ML v2.0 XSD files

So there is **no XSD-level incompatibility** preventing FlowJo 11 from reading the original `.wsp`. FlowJo 11 can open the file; the differences are in how FlowJo re-serializes the content, not in the schema itself.

What *does* change structurally:

| Element/attribute | Original export | After FlowJo save |
|---|---|---|
| `clientTimestamp` | `"NA"` | real epoch ms |
| `modDate` | export time | save time |
| `nonAutoSaveFileName` | export path | saved `.llm.wsp` path |
| Empty `<Subpopulations>` | kept | removed |
| `<Graph>` under populations | missing / minimal | added with full `<GraphEnvironment>` |
| `lineWeight` | `"1"` | `"Hairline"` |
| `percentX/Y` | often `"0"` | often dropped / `None` |
| `quadId` / `gateResolution` | absent | added (`-1` / `256`) for polygon gates |
| `Cytometer` (test14) | `GENERIC` | rewritten to `DIVA` |

These are all **FlowJo-internal serialization preferences**, not schema violations.

## Suggested changes to `export_flowjo10_workspace`

Based on the diffs, I would target these areas **before** changing any code:

### 1. Stop forcing scatter channels to `linear` when the original data uses something else
Currently the code does:

```r
if(force_XSC_linear){
  lin_trans = linearTransform(...)
  for (marker in c("SSC-A", "SSC-H", "SSC-W", "FSC-A", "FSC-H", "FSC-W")){
    transforms[[marker]] = lin_trans@.Data
    attr(transforms[[marker]], "type") = "Linear"
  }
}
```

Then it *also* writes `FSC-W` and `SSC-W` as linear. FlowJo removes those width channels from `<Transformations>` entirely when they are not actually used for gating. Recommendation: **only emit a transformation for a channel if it is referenced by a gate or axis**, and use the channel's true transform from the GatingSet rather than overriding to linear.

### 2. Preserve the original fluorescence transformation type
FlowJo converts `biex`/`fasinh`/linear fluorescence channels to `log` on save. The export currently writes:

- `biex` with `length="4096"` → FlowJo rewrites as `length="256"`
- `fasinh` with `M="4"`, `length="1"`, `W="-262144"` → FlowJo rewrites as `M="5.418539922"`, `length="256"`, `W="-262144.0000000001"`

These specific FlowJo-preferred defaults should be discovered and used at export time. Recommendation: **for fluorescence channels, write the transform parameters that FlowJo 10/11 itself would write**, rather than the R/flowWorkspace internal values. This likely means matching FlowJo's `log`, `biex`, and `fasinh` defaults (e.g., `length="256"` for `biex`/`fasinh`, `M="5.418539922"` for `fasinh`).

### 3. Fix gate coordinate / transformation inverse mapping
Tests with big population-count changes (test07, test12, test13) suggest the gate boundaries are not being inverse-transformed consistently with the way FlowJo expects them. The code already tries to apply inverse transforms, but the mismatch implies:

- The transform used for inverse may not match the transform FlowJo applies.
- Display-space vs. data-space coordinates may be confused.

Recommendation: **audit `convert_rectangle_to_flowjo10`, `convert_polygon_to_flowjo10`, and `convert_ellipsoid_to_flowjo10`** to ensure gate coordinates are written in the same space FlowJo will read them. In particular, verify that `biex`/`fasinh` fluorescence gates are inverse-transformed with the same parameters FlowJo uses.

### 4. Ellipsoid gate display-space conversion is fragile
`convert_ellipsoid_to_flowjo10` converts ellipse parameters to a 0–256 display space using `get_display_range`. This is highly dependent on the transformation ranges matching FlowJo's expectations. Recommendation: **re-check the `to_display_coords` helper** and the `get_display_range` fallback logic. Test05 / test12 use ellipsoid gates and show count drift, which could come from this conversion.

### 5. Boolean gate handling and parent references
test13 shows `/live/FITC_PE_gate` becoming unfiltered (count equals parent). The boolean gate code has a special-case for `parent & !dep` → `NotNode`, and for pure `!dep`. Recommendation: **verify that `generate_logical_node_xml` produces the correct `<Dependents>` references and that parent/child gate IDs are wired correctly** after FlowJo regenerates IDs. The fact that a gate becomes 100% of parent suggests the boolean reference is lost or points to a non-existent gate.

### 6. Cytometer detection (test14)
In test14 the export writes `GENERIC`, but FlowJo changes it to `DIVA` with `useTransform="1"`, `transformType="BIEX"`, and different min/max values. This likely triggers the cascade where all terminal subset counts become 0. Recommendation: **detect the cytometer from FCS keywords** (e.g., `$CYT`, `$INSTRUMENT`) and emit a matching `<Cytometer>` entry, or at least avoid the hard-coded `GENERIC` instrument for BD/Fortessa-style files.

### 7. Population count recomputation on open
test14 is catastrophic: all terminal populations drop to 0. This means FlowJo cannot recompute the gates from the saved workspace. The most likely causes are:

- Missing or incompatible transformations.
- Gate coordinates in the wrong coordinate space.
- Cytometer mismatch.

Fixing items 1–6 above should resolve this, but test14 should be treated as the primary regression test.

### 8. Optional cosmetic alignment
The following would make the export look more native but have no functional impact:

- Remove empty `<Subpopulations>` nodes.
- Add `<Graph>`/`<GraphEnvironment>` under each `<Population>` in group nodes.
- Use `lineWeight="Hairline"` and omit `percentX/Y`.
- Add `quadId="-1"` and `gateResolution="256"` to `<PolygonGate>`.
- Set a real `clientTimestamp` and `modDate`.

I would prioritize the functional items (1–7) over the cosmetic ones (8).

### 2026-07-01: Deep dive on `yRatio="0.5"`

`yRatio` is a display hint on `<gating:dimension>` elements inside `<RectangleGate>`. It tells FlowJo where to draw the gate along the Y-axis when the gate is defined on only one axis (or when the dimension is the X-axis of a 2-D rectangle gate). The value is consistently `0.5`, meaning "center the gate vertically at 50% of the plot height."

**Observed usage across all `.llm.wsp` files:**

| Test | `clientTimestamp` | 1-D rects | 2-D rects | `yRatio` count |
|---|---|---|---|---|
| test01 | `NA` | 0 | 0 | 0 |
| test02 | real | 2 | 0 | 2 |
| test03 | `NA` | 0 | 2 | 2 |
| test04 | `NA` | 0 | 0 | 0 |
| test05 | `NA` | 0 | 0 | 0 |
| test06 | `NA` | 2 | 0 | 1 |
| test07 | `NA` | 2 | 0 | 1 |
| test08 | `NA` | 2 | 0 | 1 |
| test09 | `NA` | 0 | 3 | 2 |
| test10 | `NA` | 4 | 0 | 2 |
| test11 | `NA` | 2 | 2 | 2 |
| test12 | `NA` | 2 | 2 | 2 |
| test13 | `NA` | 2 | 1 | 0 |
| test14 | `NA` | 0 | 12 | 0 |

`yRatio` is absent from the native FlowJo 10.5.3 reference file (`test14_flowsom.wsp`), so it appears to be a FlowJo 10.10+ serialization convention. It is **only emitted on `<RectangleGate>` dimensions**; `PolygonGate` and `EllipsoidGate` never carry it.

**Pattern for successfully saved files:**

- `test02` is the only file with a real `clientTimestamp`, i.e. the only one fully re-saved by FlowJo 10.10.1.
- In that file, `yRatio="0.5"` appears on **both** group-level and sample-level 1-D `RectangleGate` dimensions.
- In the partially-saved files, `yRatio` usually appears only on the group-level dimensions.
- The package export currently adds `yRatio` only to **group-level** `RectangleGate` dimensions (in `generate_group_subpopulations_xml`), but **not** to sample-level gates (in `generate_sample_subpopulations_xml`).

**Where to add it in `R/export-flowjo10.R`:**

1. `generate_sample_subpopulations_xml()` — line ~1753: change the sample-level `RectangleGate` `<dimension>` line from:
   ```r
   sprintf('%s      <gating:dimension gating:min="%f" gating:max="%f">', indent, dim$min, dim$max),
   ```
   to:
   ```r
   sprintf('%s      <gating:dimension gating:min="%f" gating:max="%f" yRatio="0.5">', indent, dim$min, dim$max),
   ```

2. `generate_group_subpopulations_xml()` already has `yRatio="0.5"` at line ~1974; keep it.

3. Optionally also add `yRatio="0.5"` to 2-D `RectangleGate` dimensions in both group and sample generators. The LLM files show `yRatio` on group-level 2-D dimensions, so matching that is safer.

**Recommended conservative rule:** emit `yRatio="0.5"` on **every** `<gating:dimension>` child of a `<RectangleGate>`, regardless of whether the gate is 1-D or 2-D, and regardless of whether it appears under a `GroupNode` or a `SampleNode`. This matches FlowJo 10.10.1's behavior on the only fully successful re-save (`test02`) and is harmless when not strictly required.

question — the distinction between in-memory compensated data and the raw FCS file on disk is exactly the crux of this export issue. Let me explain what actually happens, and then give you a self-contained R test you can run to verify it.

What compensation actually does

The FCS file is NOT modified on disk. Compensation is an in-memory linear algebra operation applied to the event data matrix. What does change in memory:

1. Parameter names — After compensate(), the affected fluorescence channels get renamed with the spillover prefix (usually Comp-). This is reflected in the $P*n* keywords of the resulting flowFrame/cytoframe.
2. Data values — The numeric columns for those parameters are replaced by their compensated counterparts.
3. Keyword metadata — The keyword() list of the compensated object now describes the compensated view, not the raw file.

So when flowWorkspace/CytoML builds a GatingSet from a compensated FlowJo workspace, the in-memory cytoframe legitimately has Comp-FITC-A as a parameter name. The $P*N keywords stored in the GatingSet therefore also say Comp-FITC-A.

But the <DataSet uri=".../sample14.fcs"/> element in the exported XML still points to the original raw FCS file. If the keywords claim $P8N = "Comp-FITC-A" while the FCS file on disk only has FITC-A, FlowJo will see a mismatch when it tries to re-load the raw file.

The clean fix is: the exported keywords must describe the raw FCS file, because the exported workspace is asking FlowJo to re-apply compensation itself.

Test to verify the behavior

Here is a standalone R test you can run against any FCS file with a SPILL keyword. It demonstrates that:

- the raw file keeps the original $P*N names,
- compensate() renames them to Comp-*,
- the on-disk FCS file is unchanged,
- the original names can be recovered by re-reading the raw file.

test_compensation_preserves_raw_fcs <- function(fcs_path) {
  stopifnot(file.exists(fcs_path))

  # 1. Read the raw FCS file ---------------------------------------------------
  fr_raw <- read.FCS(fcs_path, transformation = FALSE)
  kw_raw <- keyword(fr_raw)

  par_count <- as.integer(kw_raw[["$PAR"]])
  raw_pn <- vapply(
    seq_len(par_count),
    function(i) kw_raw[[sprintf("$P%dN", i)]],
    character(1)
  )
  cat("Raw $P*N names:\n")
  print(raw_pn)

  # 2. Apply compensation in memory --------------------------------------------
  spill <- kw_raw[["SPILL"]]
  if (is.null(spill)) {
    stop("No SPILL keyword found; this FCS file may not be compensatable.")
  }

  fr_comp <- compensate(fr_raw, spill)
  kw_comp <- keyword(fr_comp)
  comp_pn <- vapply(
    seq_len(as.integer(kw_comp[["$PAR"]])),
    function(i) kw_comp[[sprintf("$P%dN", i)]],
    character(1)
  )
  cat("\nCompensated $P*N names:\n")
  print(comp_pn)

  # 3. Verify parameter names changed in memory ------------------------------
  fluors <- colnames(spill)
  changed <- comp_pn[comp_pn %in% paste0("Comp-", fluors)]
  cat("\nParameters renamed to Comp-:\n")
  print(changed)

  expect_true(
    length(changed) > 0,
    info = "Expected at least one parameter to be renamed with Comp- prefix after compensation."
  )
  expect_false(
    any(grepl("^Comp-", raw_pn)),
    info = "Raw FCS keywords should not contain Comp- prefixed names."
  )

  # 4. Verify the FCS file on disk is unchanged -------------------------------
  fr_reread <- read.FCS(fcs_path, transformation = FALSE)
  kw_reread <- keyword(fr_reread)

  reread_pn <- vapply(
    seq_len(par_count),
    function(i) kw_reread[[sprintf("$P%dN", i)]],
    character(1)
  )

  expect_equal(
    reread_pn,
    raw_pn,
    info = "Re-reading the FCS file should give the same raw parameter names."
  )

  # 5. Verify original names can be recovered from raw file ---------------------
  expect_equal(
    reread_pn,
    vapply(
      seq_len(par_count),
      function(i) kw_raw[[sprintf("$P%dN", i)]],
      character(1)
    ),
    info = "Original FCS keywords should be recoverable by re-reading the raw file."
  )

  # 6. (Optional) Show that numeric values differ in memory --------------------
  # Pick the first compensated fluorescence channel
  fluor_ex <- fluors[[1]]
  if (fluor_ex %in% colnames(exprs(fr_raw))) {
    raw_vals <- exprs(fr_raw)[, fluor_ex]
    comp_vals <- exprs(fr_comp)[, paste0("Comp-", fluor_ex)]
    cat(sprintf(
      "\nExample: %s raw mean = %.3f, Comp-%s mean = %.3f\n",
      fluor_ex, mean(raw_vals), fluor_ex, mean(comp_vals)
    ))
    expect_false(
      isTRUE(all.equal(raw_vals, comp_vals)),
      info = "Compensated values should differ from raw values."
    )
  }

  cat("\nAll checks passed.\n")
  invisible(list(raw = raw_pn, compensated = comp_pn, file_unchanged = TRUE))
}

Option A: Export the in-memory cytoframe as a new FCS file

- Write a new .fcs file from the compensated/transformed cytoframe.
- Point <DataSet uri="..."/> at this new file.

- Matches how FlowJo itself saves workspaces.

- Requires the original FCS to be available at export time and at load time.
- If the original FCS path is stale, the workspace breaks.

 are right about the intended semantics. Let me restate it clearly, because it affects which export mode is correct:

Intended FlowJo semantics

A FlowJo workspace is not the data. It is a recipe that says:

1. Read the raw FCS file (uncompensated, untransformed).
2. Apply the compensation matrix defined in the workspace.
3. Apply the transformations defined in the workspace.
4. Draw the gates on the compensated/transformed coordinates.

So the exported WSP should contain:

- <DataSet uri=".../raw.fcs"/> pointing to the original file.
- <Matrices> with the spillover matrix.
- <Transformations> with the transforms.
- <Keywords> describing the raw FCS parameters (FITC-A, not Comp-FITC-A).

That is exactly what raw_fcs_dir mode does.

What is in the GatingSet after parsing?

This depends on how CytoML::flowjo_to_gatingset() is called and on the flowWorkspace version. In general:

- The root cytoframe may already be compensated and transformed in memory.
- The GatingHierarchy stores the compensation matrix and transformations as metadata.
- The gates are defined in the compensated/transformed space.

So the GatingSet contains both:
- the processed data values (for fast plotting/gating), and
- the comp/transform recipe needed to reproduce those values from raw data.

Reconstructing raw data

If the GatingSet root cytoframe is already compensated/transformed, we generally cannot perfectly reconstruct the original raw FCS from the GatingSet alone. That is why raw_fcs_dir mode requires the original FCS file.

If the original FCS is available, we should use it. We should not try to "undo" compensation/transformation numerically, because:
- Compensation is a linear operation, so it is invertible in principle, but numerically lossy.
- Transformations like biex/logicle are non-linear and not always invertible in closed form.

The clean solution is: use the original FCS file as the data source and put the comp/transform recipe in the WSP.

Which mode should be the default?

Given this, I think we should reconsider the default:

- raw_fcs_dir mode is the semantically correct export for round-tripping through FlowJo.
- fcs_output_dir mode is a fallback when raw FCS files are missing, but it changes the data file itself.

Currently I set fcs_output_dir = dirname(output_path) as the default. If your typical use case is "I have the original FCS and want a valid FlowJo workspace," then the default should probably be no default — force the user to choose, or default to raw_fcs_dir behavior by searching next to the WSP.

Key discrepancies

1. Numbering / naming mismatch. The .docx calls the supplementary material “Appendices A–E,” while the .md files call them “Appendices A–C.” This will confuse readers if both are present.
2. Missing appendices in .md. .docx Appendices D and E are not represented as standalone .md files. If the .md files are meant to replace the .docx appendices, material has been lost.
